# 建筑变化与迁移规则

覆盖 0.0.9-rc7（封装 2 / 1095..1105）到 1.2.0-rc3（封装 5 / 1126..1138）。结论全部来自反编译源码与语料实测，没有实机验证的部分单独标注。

## 1. 定义 id 是拼出来的，不是查表

| 来源 | 规则 | 源码 |
|---|---|---|
| 建筑本体 | `definition.Id`，镜像变体现场加 `Mirrored` | `BuildingDefinitionFactory.FromMeta` |
| 岛翻转 | 原名加 `_Flipped` | `Game.Core.Content.DefinitionIdExtensions.IslandFlippedSuffix` |
| 轨道 | 前缀 `Rail` + 13 个后缀（`_Forward`、`_LeftTurn`、`_TripleMerger` 等） | `TrainNavigationIslandDefinitionFactory.Suffixes` |
| 太空带/太空管 | 前缀 `SpaceBelt` / `SpacePipe` + 11 个后缀 | `SpacePathIslandDefinitionFactory.Create` |
| 太空升降段 | `{前缀}_Lift{层}{Up\|Down}{方向}`，层 1..2，方向 `Forward/Backward/Left/Right` | 同上 + `SpacePathDefinitionData.LiftDirectionAffix`、`LiftChunksByLayer` |

语料 213 个不同 id 的实测分布：161 个能在本机 `resources.assets` 里找到明文，47 个靠上面这些规则拼出来，只有 5 个解析不到 —— 全是 1118 之前的 `Layout_Normal_*`，正是改名迁移器负责的那批。

所以「资产里搜不到这个 id」不能当作「建筑被删了」，镜像、翻转、轨道、太空路径都是运行时拼名。

## 2. 建筑 id 没有改名规则，改名只发生在岛上

1.2 的 `BlueprintMigrators` 只有两项：格式迁移（图标从 `BP.Icon` 搬到追加数据）和候选迁移 `PassthroughMigrator`（`[1126, 1137] → 1138`，什么都不改）。建筑 id 层面零改名。

岛定义的变化集中在 `GameMigrators`：

| 变化 | 版本门 | 蓝图迁移器里生效 | 说明 |
|---|---|---|---|
| 9 条基础台改名 `Layout_Normal_*` → `Foundation_*` | 1118 | 是 | `IslandDefinitionRenameMigrator`，读入时 `version < 1118` 才改 |
| `Layout_TrainStation` → `Layout_TrainQuickStation` | 1114 | 是 | 同上 |
| 轨合并器左右互换 `Rail_LeftFwdMerger` ↔ `Rail_RightFwdMerger` | 1110 | 是 | 数据没变，只是两种合并器的 id 对调 |
| 列车生产器原点后移一格 `(-1, 0, 0)` | 1117 | 是 | `IslandInstanceOriginOffsetMigrator`，需要生产器 id 清单，工具尚未实现 |
| 删除 4 个隧道岛（太空带/太空管出入口） | 无门 | **否** | `BlueprintMigrators` 显式过滤掉 `IslandDefinitionDeletionMigrator`，蓝图里的旧隧道不会被删 |

## 3. 字节串分叉：多数落在状态上

建筑本体字段（`X/Y/L/R/T/C`）从 1085 之后没再变过，变的是 `C`（建筑配置）和 `S`（岛状态）两个 base64 字节串的内部布局。每个数据序列化器按 `visitor.Version` 自己分叉，1.2.0-rc3 全树共 86 处、59 个文件：

| 版本门 | 常量 | 受影响的数据类 |
|---|---|---|
| 1098 | `RemoveIslandConfigurations` | 读卡器、各类逻辑门状态 |
| 1100 | `AddStructuresForStepsAndTicks` | 晶体生成器、快线通道、流体包 |
| 1102 | `AddSimulatorState` | 全局信号接收器配置、仿真状态 |
| 1103 | `ChangeSignalConductorSerialization` | 显示器、读卡器、四种逻辑门 |
| 1106 | `Add3DPlatforms` | 全局区块坐标（旧坐标没有 Z） |
| 1107 | `RemoveConfigurationFromSpacePaths` | 太空传送带/合并器/分流器 |
| 1109 | `UnifyBeltLaneLength` | 传送带通道、晶体生成器、染色器 |
| 1110 | `IncreaseSpacePathBandwidth` | 合并器、分流器、优先分流器 |
| 1112 | `ChangeBeltFilterSerialization` | 传送带筛选器 |
| 1114 | `AddOptionalEntityConfiguration` | 传送带端口、岛布局 |
| 1116 / 1131 | `ChangeTrainSerialization` / `ReworkExchangeFilter` | 交换层筛选配置 |
| 1121 | `AddTrainTransferStationsSerialization` | 货运交换编排 |
| 1127 / 1132 | `ItemProducerCounting` / `RevertItemProducerCounting` | 转换器枢纽、物品生产器 |
| 1128 | `MemoryFriendlyFastBeltPathLaneSerialization` | 快线通道 |
| 1137 | `IncreaseTrainPackageCapacity` | 列车货舱、列车状态 |

按文件再分一遍：这 86 处里绝大多数是 `SimulationState`（传送带通道、晶体生成器、逻辑门、端口收发、转换器、快线、列车货舱），落在**配置**上的只有 `GlobalSignalReceiverConfiguration`（1102）与 `ExchangeLayerFilterConfig`（1131）两个类。处理方式分别是清空状态（第 8 节）与逐类改写（第 7 节）。

## 4. 游戏自己怎么处理认不得的建筑

`BlueprintSanitizer.TryRemoveUnknownEntries`（1.2）：

- id 在游戏内容里完全不存在 → 抛异常，蓝图进不去；
- id 存在但当前会话/模式没有（内容未解锁、模式差异）→ 静默移除该条目。

也就是说旧蓝图能不能进游戏，卡在版本窗口和 id 解析，不卡在「有没有迁移器处理这个建筑」。

## 5. 版本窗口只是保守闸门

蓝图里的 `V` 取全份条目的最高版本，游戏只按它判断要不要跑迁移链，不代表每件东西都变过。1.0 写的纯传送带蓝图和 1.2 的内容完全一致，只是 `V` 停在旧值；反过来 `V` 是新的也可能混着旧岛。窗口外拒绝加载是保守策略，真正的迁移要按条目内容做。

| 版本 | 封装 | 受理 `V` |
|---|---|---|
| 0.0.9-rc7 | 2 | `[1095, 1105]` |
| 0.1.1 | 3 | `[1105, 1122]` |
| 1.0.3-rc3 / 1.1.0-rc2 | 4 | `[1130, 1137]` |
| 1.2.0-rc3 | 5 | `[1126, 1138]` |

## 6. 内容级替换：地下隧道 → 太空层走线

0.0.9 的隧道是成对的入口/出口岛，中间的地下通道不占区块，长度记在入口 `S` 的 `ForwarderState.Length_S`。1.2 删掉这 4 个岛，改由三层太空层走线接替：地面升到 z=1、横穿、再降回地面。

替换按 1.2 的岛定义几何确定（`SpacePathIslandDefinitionFactory`、`SpacePathDefinitionData`）：

| 旧条目 | 新条目 | 位置 |
|---|---|---|
| `Layout_SpaceBeltTunnel_Entrance` / `Layout_SpacePipeTunnel_Entrance` | `SpaceBelt_Lift1Up{方向}` / `SpacePipe_Lift1Up{方向}` | 入口列 `Z=0` |
| 中间通道 | `SpaceBelt_Forward` / `SpacePipe_Forward` | `Z=1`，跨度内每列一段 |
| `..._Exit` | `{前缀}_Lift1Down{方向}` | 出口列 `Z=1` |

- 方向取入口到出口的轴向位移。旧版放置只能拖直线（`SpacePathTunnelPlacement.ProjectVectorToDirection`），所以配对的两端必然同轴。
- `R` 用 `GridRotation` 编号：东 0、南 1、西 2、北 3，后缀东 `Forward`、南 `Right`、西 `Backward`、北 `Left`。
- 升降段占同一列的 z0 和 z1（`LiftChunksByLayer`），输入朝西、输出朝东；`Lift1Down` 锚点在上层，所以出口列写 `Z=1`。
- 走廊在地面上方，z0 被建筑占着不影响 z1 走线；只要入口、出口两列的 z0 与 z1 空着即可。
- 隧道里正在运输的货物丢弃：旧 `S` 不搬，新岛按空配置重建。

语料实测：392 份蓝图里没有隧道实例；只有 1 份 0.0.9 蓝图含 3 个 `Layout_SpaceBeltNode`（旧太空节点网）。

## 7. 特殊建筑迁移清单

只列身份或形态真的变了的，纯传送带、管道、建筑本体这类保持原样。

| 类别 | 旧形态 | 1.2 的替代 | 处理 | 状态 |
|---|---|---|---|---|
| 地下隧道（传送带） | `Layout_SpaceBeltTunnel_Entrance/Exit` 成对，地下通道不占区块 | `SpaceBelt_Lift1Up/Down{方向}` + `SpaceBelt_Forward`，走 z=1 | 按入口→出口位移重建走线 | 已实现 |
| 地下隧道（流体） | `Layout_SpacePipeTunnel_Entrance/Exit` | `SpacePipe_Lift1Up/Down{方向}` + `SpacePipe_Forward` | 同上 | 已实现 |
| 太空节点网 | `Layout_SpaceBeltNode` / `Layout_SpacePipeNode`，1 区块 3 车道、连线自由 | `SpaceBelt_*` / `SpacePipe_*` 网格岛（直行、四种转向、分流与汇合），走 z=1 | 解 `C` 里的连线换成对应岛 | 已实现（U 形节点无对应岛，保留并报出） |
| 轨道节点网 | `Layout_RailNode`，同样按连线选型 | `Rail_*` 网格岛 | 同上 | 连线布局未解，按相邻关系兜底 |
| 基础台 | `Layout_Normal_1/2/3_L/3x1/3x2/4_2x2/4_T/5_Cross/9_3x3` | `Foundation_1x1/1x2/L3/1x3/2x3/2x2/T4/C5/3x3` | 纯改名 | 已实现 |
| 列车站 | `Layout_TrainStation` | `Layout_TrainQuickStation` | 纯改名 | 已实现 |
| 轨合并器 | `Rail_LeftFwdMerger` 与 `Rail_RightFwdMerger` 名称对调 | 同左 | 互换 id | 已实现 |
| 列车生产器 | 原点 `(0,0,0)` | 原点后移 `(-1,0,0)`，按岛屿旋转折算 | `Layout_TrainProducer_*` 坐标补偏移 | 已实现 |
| 受控信号接收器 | `C` = int 索引 + 有效位（5 字节） | `C` = 通道 uid（4 字节） | 1102 之前按 `FromRandomOperatorShape` 换算 | 已实现 |
| 交换层筛选 | `C` = 层号列表 | `C` = 位掩码 | 1116..1131 之间按列表转位掩码 | 已实现 |
| 岛条目层号 | 1106 之前没有 `Z` | `Z=0` | 补字段 | 已实现 |
| 蓝图图标 | `BP.Icon` 内嵌 | 追加数据段 | 搬迁 | 已实现 |
| 岛 `BinaryVersion` | 封装 ≤4 会写 | 1.2 已取消 | 删字段 | 已实现 |

传送带筛选器、转换器枢纽、快线通道、列车货舱这几类，版本门卡的都是**状态**布局，不是配置布局，处理方式见下一节。

## 8. 状态字节串一律清空

把 1.2 的 86 处 `visitor.Version` 分叉按文件过了一遍：绝大多数落在 `SimulationState` 一类——传送带通道、快线通道、晶体生成器、染色器、各类逻辑门、端口收发、转换器枢纽、列车货舱与交换编排。真正落在**配置**上的只有两个类：

- `GlobalSignalReceiverConfiguration`（1102，见上一节）；
- `ExchangeLayerFilterConfig`（1131，见上一节）。

建筑条目只有 `C`，没有状态字段；岛的 `S` 是瞬态状态（轨道占用、缓冲内容、计数进度），进游戏就会重建。所以升级时把旧蓝图的岛 `S` 直接清空，比对着一堆旧布局逐字节解码更可靠，也不会把旧进度当成新语义读。

## 9. 旧节点的 `C` 布局

`IslandLegacyConfigMigrator`（1098 及更早）规定节点配置的第一个字节是类型：

| 首字节 | 类型 | 后续 |
|---|---|---|
| 0 | 空 | 丢弃 |
| 10 | 轨道节点 | `byte 连线数`，每连线 `byte 输入面, byte 输出面, int 颜色位掩码` |
| 20 | 太空路径节点 | `byte 连线数`，每连线 `byte 输入面, byte 输出面` |

方向编号东 0、南 1、西 2、北 3，`(输入面, 输出面)` 表示「从哪一侧进、往哪一侧出」。1.2 的每座网格岛正好是一组这样的连线对，所以按对表直接换，顺带定出流向与旋转：

| 岛 | 本地连线对 |
|---|---|
| `_Forward` | 西→东 |
| `_LeftTurn` / `_RightTurn` | 西→北 / 西→南 |
| `_LeftFwdSplitter` / `_RightFwdSplitter` / `_YSplitter` | 西→北 + 西→东 / 西→东 + 西→南 / 西→北 + 西→南 |
| `_LeftFwdMerger` / `_RightFwdMerger` / `_YMerger` | 西→东 + 南→东 / 西→东 + 北→东 / 北→东 + 南→东 |
| `_TripleSplitter` / `_TripleMerger` | 一进三出 / 三进一出 |

样本 `14 02 00 00 00 03` 解出 2 条连线（东→东、东→北）：东→北是 1.2 的右转或左转，但东→东是 U 形，1.2 没有单区块掉头岛，这条保留原样会整份蓝图导不进去（`BlueprintSanitizer` 对两个目录都不认识的 id 直接抛 `ArgumentException`），所以按「丢弃 + 报告坐标」处理。

轨道节点的颜色位掩码没解成映射：新旧都是 `int`，但旧节点是「每条连线一个掩码」，1.2 的轨道岛配置是 `RailConfiguration`（`byte 连接数` + 每连接 `int`），顺序要跟着岛定义的连接器顺序走。现在统一写「全色通行」（7 色掩码 `0x7F`），报告里标 `needs_review`。

## 10. 还没迁移的

| 项目 | 原因 |
|---|---|
| 轨道节点的每连接颜色掩码 | 需要先确认 1.2 各轨道岛连接器的排列顺序，语料里没有旧轨道节点样本可对照；现按全色写 |
| U 形与十字太空节点 | 1.2 没有单区块掉头岛，也没有 2 进 2 出的十字岛，只能丢弃并报坐标 |
| bundle 内的完整 id 全集 | 压缩包扫不到，要引 UnityPy 解包 |

## 11. 工具的现状

`upgrade.py` 按顺序做：版本与格式、删 `BinaryVersion`、岛条目补 `Z`、岛改名与轨合并器互换、地下隧道改太空走线、节点网换网格岛、生产器补偏移、清空旧岛状态、改写两处分叉配置、图标搬进追加数据，最后按本机 id 目录核对每一条 `T`。

`catalog.py` 的目录分三类结果：`asset`（资源里有的定义）、`generated`（工厂按前缀后缀拼出来的）、`removed`（1.2 已彻底移除、但字符串还残留在资源里）。第三类一并进报告，避免「能搜到就算存在」的误判。

## 12. 仍需实机确认

1. 隧道改线与节点换岛后的实际连通性。升降段、网格岛的朝向都在源码里核对过，但没进游戏验证。
2. 3 向以上节点按分流生成后的流向。
3. 清空岛状态后游戏是否如预期重建（尤其列车与转换器）。
